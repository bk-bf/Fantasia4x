Fantasia4x Check Map

Every check in the repository, what starts it, and where it sits in the one chain GitHub starts and records. A push or a merge starts the chain; so does one command.

pnpm chainpushes the branch, starts or follows its chain on GitHub, and streams the run to its result. --pre runs the pre-check alone.

It replaces pnpm ci:local, which ran the checks on ubuntuserver and left no record. pnpm reserves the name ci for itself, so the command is chain.

The chain

Six stages, in order

Each stage starts only when the one before it passes, so a failure costs the time of the stage it fails in. Stage 0 stays on the machine because it decides whether a write may happen at all; stages 1 to 5 are started and recorded by GitHub.

Placement

Why each job runs where it runs

ubuntuserver is an Intel Xeon E5-2420 v2 from 2013 at 2.2 to 2.7 GHz, and its runner service sits at Nice=10, CPUWeight=20. GitHub's runner is free for this public repository and has faster cores. Speed decides every job except the two that measure time or cost.

Pre-check, small change 65–90 s about 105 s GitHub's runner speed: svelte-check 46 s and eslint 39 s alone on the server
Pre-check, 34 changed game files 364–408 s 610 s GitHub's runner speed, even for wide test runs
Rust instruction counts 27–36 s 51 s GitHub's runner speed

CodSpeed, 180-tick windows not comparable 1,065–1,149 s ubuntuserver stability, over speed
Ticks per second never run 320 s ubuntuserver one fixed machine, assumed

CodSpeed stays on ubuntuserver, though it would finish sooner on GitHub's runner.

On GitHub's runners the machine changes from run to run, and identical code read up to 2.6% apart; CodSpeed flagged three commits that changed no game code. On ubuntuserver four runs of the same code agree within 0.43% in instructions. A measurement that moves 2.6% on its own cannot tell a real 1% cost from noise, and a slower answer that holds is worth more than a fast one that does not.

Pre-check and leg times from the last 25 CI runs; server times from ci:local and a timed run at load average 5.6. The server's large related-test run exited 1, so at least one test in that set fails on 48da25ba.

Commands

What starts the chain

Three things start it: a push, a merge, and pnpm chain. Everything else is either a tool for working, whose results nobody relies on, or not a check.

pnpm chain [--pre]the one command
Replaces

pnpm ci:local [--quick], which ran stage 1 and every leg on ubuntuserver in place and left nothing on GitHub.

Does

Pushes the branch, follows its pull request's run or starts the chain on the branch, and streams the run to its result. --pre runs the pre-check alone.

git pushto a pull request branch or to dev
Before

One job held stage 1 and the GitHub legs; CodSpeed and ticks per second started beside it without waiting.

Now

Stage 0, then stages 1 to 3. The pre-check is its own required job, and every leg waits for it.

merge into devboard-sync.py or by hand
Before

Required the one check job named "pnpm check, related tests, seams and work pins".

Now

Requires Pre-check and Measurements; the merge commit's push to dev starts the chain again.

pnpm check · test:related · testthrough remote/run.mjs
Before

Run on the server; agents ran them before a push as if they were the check.

Now

The working loop while editing, and nothing more. No rule requires them and no card depends on them.

pnpm audit:promotedev into main
Now

Pushes the candidate to promote/main; promotion repeats the check steps in its own file.

Proposed

promotion calls CI as a reusable workflow with the scope off, so every check is defined once.

fixer · revieweraudit/fix.mjs, audit/review.mjs
Now

The fixer runs pnpm check and the related tests before it pushes; the reviewer reruns them on a fresh merge and runs a headless session for headless cards.

Proposed

The fixer reads stage 1 from GitHub; the reviewer keeps only the headless session.

./audit.sh · gpu-probe.yml · build.ymlby hand
Now

Combat audits on another machine; GPU research on a rented one; packaging on version tags.

Proposed

Combat audits become a dispatchable job; GPU timing joins stage 2 once #123 settles; packaging is not a check.

Still open

Decisions for later

  1. Report-only extras in stage 1.

    Add unused exports, copy-paste and the threat model as warnings on the run page, or leave them out.

  2. The fixer trusts stage 1.

    It stops its own final run and reads the result from GitHub. The model still runs tests while it works.

  3. The reviewer drops its test re-run.

    Branch protection already requires stage 1 on an up-to-date branch, which is the same run.

  4. Promotion reuses CI.

    promote.yml calls check.yml with the scope off, so every check is written once.

  5. Ticks per second on GitHub's runner.

    It compares the old and new code inside one job, which may cancel the machine difference. Three runs there would show whether it needs ubuntuserver.
