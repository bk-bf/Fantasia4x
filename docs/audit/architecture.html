audit

A ledger of every question ever asked about this codebase, which object it was asked about, and which version of that object answered.

"I audited the code" cannot be checked. Nobody can say which of the 6,233 objects in this repository anything ever read, under which question, or whether the answer still describes the code as it stands today.

This tool replaces the claim with a table. Every auditable object gets a key that does not move when lines shift, and a hash of its exact source. Every rule gets a hash of its own text. An answer is stored against the pair it was produced under, so coverage is a SELECT count(*) rather than a memory of what someone looked at.

The pipeline

What counts as an object

An object is a symbol: a thing with a name, a start line and an end line. Indexing walks the repository and records one row for each, with the exact bytes it spans and a hash of them.

KindCountWhat it is
data-row2995One entry in a .json data file: an item, a recipe, a terrain
function2023A named function in TypeScript or in a Svelte script block
method704A method on a class, keyed by Class.name
table355A declared array or record read as a lookup
markup112The template half of a Svelte component
store41A Svelte store or a rune-backed state object
accessor3A getter or setter

The key is <file>::<Class.name>#<ordinal>, which survives an edit above it. Adding a blank line at the top of a file does not invalidate anything in it.

Indexing also computes flags — 22 facts a script can decide by reading the symbol alone, such as allocatesArray, emptyCatch, hasPlayerFacingText, rendersIdExpression, hasTier. A flag is never an opinion about the code; it records that a shape is present, so a rule can be pointed at the symbols where its question could even apply.

A verdict expires by itself

Three hashes decide whether an answer still stands:

HashOverChanging it means
content_hashThe symbol's exact source sliceThe code was edited; every answer about it re-opens
rule_hashThe rule's question, trigger and evidence contractThe question changed; every answer to it re-opens
dep_hashThe symbols this one callsA callee moved under it

A row in verdict carries the hashes it was written under, and a UNIQUE index over (symbol_key, rule_id, content_hash, rule_hash). There is no stale column, so there is nothing to forget to set. audit plan rebuilds the pending set by joining symbols against active rules and subtracting the verdicts whose hashes still match.

The same check runs again at submission. If the source moved while a batch was with the model, the answer is refused and the work item stays open. A worker cannot record a judgement about code that no longer exists.

Three tiers, and a ratchet

Every rule is assigned to exactly one tier, and has to justify why the cheaper tier below it cannot decide the question.

TierMechanismDecides
T0svelte-check, eslint, audit t0Types, declared constants, architecture seams
T1vitest, HeadlessSessionBehaviour that runs
T2The model loopWhat a reading of prose against code decides

audit demote lists T2 rules that have failed the same way often enough to be worth writing as a static check. Once written, the rule's status becomes demoted and it stops costing tokens. The expensive tier is meant to shrink.

A rule carries the question, the evidence a failure has to produce, the shapes that are not findings, and a trigger the harness evaluates:

{
  "id": "S01",
  "name": "restated-roster",
  "family": "single-source",
  "tier": "T2",
  "question": "Does this symbol list members of a set that is declared elsewhere?",
  "fail_requires": ["file:line of the declaration", "file:line of the restatement"],
  "not_a_finding": ["a narrowing that names a subset on purpose"],
  "trigger": { "all": [{ "kind_in": ["function", "table"] }, { "min_loc": 4 }] },
  "status": "active"
}

Trigger clauses read the symbol and its own metadata: file_glob, kind_in, layer_in, name_matches, exported, min_loc, any_flag, matches, composed with all / any / not.

There is no trigger for "is this tested" or "is this reached from the tick loop". Those are questions about the rest of the repository. Answering them in the harness would mean keeping a second copy of the call graph in step, and a copy that drifted would stop firing quietly — which reads as clean code rather than as a question nobody asked. The rule states the question instead, and the model has to search for the answer and cite path:line.

Four answers, and what each one costs to give

StatusCountRequirement
pass360The default. Nothing more is asked for
fail274Every item in that rule's fail_requires, plus a summary
n/a213Must name the trigger clause it believes did not hold
undecidable0Must name exactly what was missing

The requirements are checked in lib/verdict.mjs, not requested in the prompt. A failure that arrives without its citations is rejected and the work item stays pending, so the cheapest way for a model to finish a batch is to answer pass honestly.

undecidable exists so that guessing is never the only way to close an item, and a rule with a high undecidable rate is a badly scoped rule. Both that rate and the n/a rate are visible per rule in audit status, which is how a family gets caught firing on symbols its question does not fit.

Claiming work

A batch is one symbol and up to 40 of its pending rules. Reading one symbol once and answering every open question about it is cheaper than reading it forty times, and the answers are independent rows regardless.

Claims are taken inside BEGIN IMMEDIATE with a changes() check, so any number of processes on any number of machines can share one ledger without two of them claiming the same work. A claim carries a 30-minute lease. An expired one is deleted at the top of the next claim, and its work row returns to pending, so a worker killed mid-batch costs one batch. audit release returns a worker's claims immediately.

Spending against a five-hour limit

The account has a rolling five-hour usage window. Running until it is empty and then stopping would leave hours with nothing running and no capacity left for anything done by hand. The gate in lib/pace.mjs spreads the spend across the window instead.

The target rises from wherever usage stood when the window opened to the ceiling by the time it closes. Usage above the target means wait; below it means go. The ceiling is a number on the page, so lowering it reserves headroom for work done by hand without stopping the audit.

One implementation of that formula. The dashboard used to compute its own version of the target for display, and the two disagreed — the page showed a number that no worker was gating on. audit.mjs tick now returns the schedule and the monitor prints it.

What starts a run

The page at /audit never touches the ledger and never starts a process. A button writes a request file; one command reads it.

tick decides one thing: whether a runner should be alive right now. It is alive when the audit is not paused, a run window is open, and work is pending.

Start opens a window

Of the requested length, with the requested workers and model.

Resume reopens the last one

If it has closed. That is what lets Resume start the audit from a standing stop.

Pause kills the runner

run.mjs exits rather than idling. The next tick after a resume starts it again with the hours the window has left.

The window closing ends it

Nothing relaunches after that until a button asks. Five launches that die inside two minutes close the window and record why.

The runner is a unit, not a child process. A process spawned by audit-monitor.service sits in that unit's cgroup, and systemd tears the cgroup down when a Type=oneshot service finishes. A run started that way was killed within a minute every time while the button reported success. systemd-run --user gives the runner its own cgroup, and systemctl --user status fantasia-audit-run is its status.

Findings become issues

A verdict is a row. An issue is a unit of work. audit issues turns one into the other by grouping open failures by (rule, two-segment module path): a rule firing forty times across one directory is one class of defect, and the class is what a single branch can close. Each issue carries every citation the audit demanded before it would record the failure.

tools/issue.mjs is the only writer. Direct gh issue create is denied in .claude/settings.json, because an issue written by hand skips the repairs and the refusals:

  • A path:line written in prose becomes a permalink pinned to the commit the audit indexed. A citation names a line, and a line is only true at one revision.
  • A label outside tools/audit/labels.json is refused, naming the nearest real one.
  • A body under roughly 240 characters, or with no citation, or with no remediation checkbox, is refused as a stub.
  • Four classifications are required on every issue: severity, kind, origin and verify. An issue missing one cannot be sorted or costed.

The board is projects/4, and its columns are an order: Backlog → Ready → In progress → In review → Done, with Blocked on you and Needs playtest off to the side.

Moving the card is the only gesture. board-sync.py runs on the same 20-second tick as the monitor and derives the ready, needs decision and verify labels from the board's Status and Verify fields. A label edited by hand is overwritten within a minute. Severity, kind, origin and the rule name are never touched — they describe the finding, not its state.

The field is set at triage, not at review, so the cost of an item is visible before anyone starts. An audit that reports creatures dying faster cannot say whether that is the game he wants; a measurement that could settle the question means the item is not a playtest.

The fixer

fix.mjs takes one issue, works it in a git worktree off origin/main on a branch fix/<slug>, and writes the attempt up as a comment on the issue. Nothing is committed unless pnpm check and the related tests are green, and nothing is pushed at all — whether the branch reaches main is decided by reading git diff main...fix/<slug>.

An attempt that cannot get green commits nothing, keeps its worktree, writes the failure to the issue, and returns the issue to the pool. A run interrupted by a signal releases its issue before exiting; without that, a killed run leaves an issue marked in progress that no later run will ever pick up.

The fixer never opens a pull request. This is a solo repository, so a branch merged with --no-ff and an issue closed against the merge commit says everything a review page would, and several related fixes belong in one branch rather than one branch each.

The nightly run

deploy/ holds a systemd user timer whose ExecStart points into this checkout, so the repository owns the units and install.sh symlinks rather than copies. nightly-audit.sh runs in this order, and the order decides whether the night is spent on current code:

StepDoesSpends
1Fetch and fast-forward main. A dirty tree stops the runNothing
2audit index and audit plan — only what moved re-opensNothing
3run.mjs until the budget runs outTokens
4audit issues — failures onto the boardTokens
5fix.mjs --next, only on issues a person marked readyTokens
6mon run with the night's numbers, readable from a phoneTokens

A flock stops a second night starting on top of one that overran. The server's clock is UTC, so the timer carries an explicit Europe/Berlin; a plain 0 4 * * * would fire at 06:00 local in summer and shift at every change. The default node there is v20, which has no node:sqlite, so the script pins v24.19.0.

Rules that look arbitrary and are not

  • A draft rule is planned but never claimed. That is how a rule's trigger can be measured against the real repository before it costs anything to answer.
  • The model runs in plan mode. Its tools are read-only, so it cannot change the code it is describing, and its working directory is the checkout so its searches resolve against the version the batch is about.
  • Every batch is a fresh process with no memory. The ledger is the only state, so a run can be killed at any moment and resumed with no loss beyond one batch.
  • The ceiling defaults to 95%, not 100%. The last five percent is what is left for work done by hand while the audit is running.
  • Nothing marks its own work ready. An audit that raised its own findings and then acted on them would be a loop with nobody in it.
